MTF Nu-7 "Hammer Down" · Database concept · 02 Nov 2026

From Google Sheet to Nu-7 Database

The workbook has 30 tabs. They hold four kinds of data: master data (who is who, which rank), logs (duty, trainings, tryouts, strikes …), views calculated from those (Roster, Activity Hub, Overview) and raw Google Forms responses. A database only stores the first two. Everything else is calculated live from them, so it can no longer drift apart.

02 · Database diagram

The data model

The key building block is person, identified by Steam ID. Everyone who has ever appeared (recruit, member, former member, blacklisted) is exactly one person. Names change, the Steam ID doesn't. In the sheet, the same Steam ID shows up under as many as three names (see section 06).

03 · Requirements on the website

Promotion board: keep ticking requirements with a click

This is how the "Promotion Requirements" tab would look on the website. Requirements and members come from your sheet. There are two kinds of requirements. Manual ones (licences, hacks, basic training) are ticked by an officer with a click, which is saved with their name and the time. Automatic ones (activity, cooldown, later also "host 1 training" or "perform a tryout") are calculated by the database itself from the logs. The switches at the top turn each requirement on or off for a stage.

Demo: changes stay in this browser window only and are not saved anywhere. Calculated automatically here are activity (roster hours ≥ 6 h per week, an assumption based on the Activity Hub) and cooldown (the roster's "Cooldown" column). In the real database both come from duty_log and rank_change.

04 · Calculated, not typed

What the database works out itself

Today these values are separate columns in the sheet that have to be maintained by hand or pulled across tabs with formulas. In the database they are never stored, but calculated fresh on every query.

Sheet columnCalculation
StrikesSum of strike.weight where expires_on > today and not successfully appealed
Hours · Hrs / 3 Days · Hrs RemainingSum of duty_log.hours for the current week or last 3 days; remaining = rank.weekly_hours_required − hours
Status (Active, Semi-Active …)LOA/ROA if today falls in a leave period, otherwise a level based on weekly hours. Thresholds are a setting, manual exceptions via status_override
Last Promotion Date · CooldownLatest rank_change of kind "promoted"; cooldown is active while effective_on + rank.cooldown_days > today. Notes like "Real Promotion date …" are no longer needed
Last LOA/ROA Start/Expiry/TypeLatest entry in leave
Medals (Roster) · MedalCodemedal_award grouped per person
Overview: personnel, slots 47/65, fundsCounts by rank_category, sum of rank.max_slots, totals over fund_transaction
Management: trainings/tryouts in the last 7 daysCounts in training / tryout
Pre-Tryout CheckerWhen a tryout is entered, the database checks v_active_blacklist for the Steam ID (expired and revoked entries are left out) and warns straight away
05 · The website

Pages, roles and tech

Pages

  • Roster: publicly readable, grouped by category and rank, showing open slots
  • Personnel file: everything about one person on one page (ranks, strikes, LOAs, medals, trainings, duty hours). Fields are editable in place
  • Promotion board: like the demo above, with a "Promote" button that creates the rank_change
  • Log forms: duty, training, tryout + quiz, strike, LOA. They replace the Google Forms; names are picked from a search instead of typed
  • Overview: headcount, activity, funds, weekly goals
  • Admin: manage ranks, requirements, medals, battalions

Roles

  • Guest: view roster, medals, Memorial Hall
  • Member (Discord login): own file, log duty and LOA
  • NCO (CPL+): log trainings and tryouts, tick requirements up to SGT
  • Officer (LT+): strikes, promotions up to CSG, all requirements
  • RegCom: everything, including changing requirements and ranks, blacklists

The role comes from the rank plus unit_role (e.g. Roster Manager). It is enforced in the database itself (Row Level Security), not only in the interface.

Recommended stack

  • Supabase: Postgres, Discord login, permission rules and an automatic API in one; the free tier is enough for this amount of data
  • Frontend: SvelteKit or Next.js, hosted on Vercel
  • Usable right away: to start, Supabase's table editor (or NocoDB on the same database) is enough for editing. The custom pages can be added step by step
  • Optional: a Discord bot for /duty 2 or /loa

Data problems the database prevents

J. 'GHOST' Ken (currently Sergeant) has the same Steam ID STEAM_0:0:634558185 as "Boris 'Ghost' Ken" on the blacklist (03/03/2025) and "Juan 'GHOST' Ken" in the medals. The blacklist entry has since been revoked, but the sheet has nowhere to record that: the "Appealed / Unblacklisted" checkbox is empty and there is no date, reason or name of who lifted it. The new blacklist_appeal table keeps that history, so the pre-tryout check knows the ban no longer applies.

07 · Migration

Four steps from sheet to website

1 · Schema & import

  • Create the tables in Supabase (SQL below)
  • Import script: read every tab as CSV, merge people by Steam ID
  • Output a conflict list (see 06) and resolve it by hand

2 · Editing without custom pages

  • Set up Discord login and roles
  • Maintain data via the Supabase editor / NocoDB
  • Keep the sheet read-only alongside

3 · Custom website

  • Roster, personnel file, promotion board
  • Log forms replace Google Forms
  • Overview dashboard

4 · Automate

  • Automatic requirements from logs
  • Strike expiry, LOA end, cooldown without manual work
  • Optional Discord bot and weekly report

  id uuid primary key default gen_random_uuid(),

  person_id uuid references person on delete cascade,
  name text not null,
  seen_from date,
  primary key (person_id, name)

create table membership (
  id uuid primary key default gen_random_uuid(),
  person_id uuid not null references person,
  rank_id int not null references rank,
  recruited_at date not null,
  left_at date,

  discharged_by uuid references person,

create unique index one_active_membership on membership (person_id) where left_at is null;

-- blacklist entries that still apply (used by the pre-tryout check)
create view v_active_blacklist as
select b.* from blacklist b
where (b.expires_on is null or b.expires_on > current_date)
  and not exists (select 1 from blacklist_appeal a
                  where a.blacklist_id = b.id and a.decision = 'revoked');

-- ===== Roster view (replaces Roster / Database / Activity Hub) =====
create view v_roster as
select m.id as membership_id, p.display_name, p.steam_id, p.discord_username,
       r.code as rank, r.sort_order as rank_order, rc.name as category,
       coalesce(s.points, 0)              as strikes,
       coalesce(d.week_hours, 0)          as week_hours,
       greatest(r.weekly_hours_required - coalesce(d.week_hours,0), 0) as hours_remaining,
       lp.effective_on                    as last_promotion,
       (lp.effective_on + r.cooldown_days > current_date) as on_cooldown,
       coalesce(m.status_override, lv.type,
         case when coalesce(d.week_hours,0) = 0 then 'Inactive'
              when d.week_hours < r.weekly_hours_required then 'Semi-Active'
              when d.week_hours < 25 then 'Active'
              when d.week_hours < 30 then 'Very-Active'
              else 'Extremely-Active' end) as status
from membership m
join person p on p.id = m.person_id
join rank r on r.id = m.rank_id
join rank_category rc on rc.id = r.category_id
left join lateral (select sum(weight) points from strike
  where person_id = p.id and expires_on > current_date and appeal_status <> 'granted') s on true
left join lateral (select sum(hours) week_hours from duty_log
  where person_id = p.id and logged_on >= date_trunc('week', current_date)) d on true
left join lateral (select effective_on from rank_change
  where person_id = p.id and kind = 'promoted' order by effective_on desc limit 1) lp on true
left join lateral (select type from leave
  where person_id = p.id and current_date between starts_on and ends_on limit 1) lv on true
where m.left_at is null;

The status thresholds (25 h / 30 h) are estimated from the current roster values and belong in a settings table later.
